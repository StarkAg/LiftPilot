LiftPilot: Smart Lift Stoppage Scheduler for Crowded Buildings

Project type: Frontend scheduling prototype | Stack: React 18, Vite, CSS | Deployment-ready static app

LiftPilot is a smart lift scheduling prototype designed for rush-hour movement inside crowded buildings. Instead of making the lift stop at every requested floor, the system recommends the best one-stop or two-stop plan so that the lift can move faster while still keeping passenger walking effort low. The project is based on the idea that during heavy traffic, a lift should behave like a shared transport system, not like a private elevator. This improves throughput, reduces unnecessary stoppages, and keeps the line moving.

The prototype is implemented as a single-page React application with a tablet-style interface for floors 1 to 15. A user taps destination floors, the system queues all requests, and the scheduler immediately computes the recommended stoppages. The UI also shows total riders, active floors, total cost, selected stops, and a detailed calculation panel. That panel makes the solution explainable because it shows the sorted requests, the weighted percentile used for a one-stop plan, every possible two-group split, and the total cost comparison before choosing the final result.

Core Technical Idea

LiftPilot does not use AI or machine learning. It uses a deterministic weighted cost function. This makes the system fast, transparent, and suitable for real-time decision making. The model assumes that walking upstairs is more difficult than walking downstairs, so upward stair movement is penalized more heavily than downward movement.

If a passenger wants floor f and the lift stops at floor s, the walking cost is:

cost(f, s) = upWeight * (f - s), if f > s cost(f, s) = downWeight * (s - f), if f <= s

In the current implementation, the default parameters are:

  • upWeight = 3
  • downWeight = 1
  • stopPenalty = 8
  • maxStops = 2

This means that walking up by one floor is treated as three times more costly than walking down by one floor. Each extra lift stop also adds a penalty, because every stop increases waiting time and reduces operational efficiency.

For a request set R, the total walking cost for one stop s is:

C_walk(s) = sum over all f in R of cost(f, s)

The full one-stop objective becomes:

C_1(s) = C_walk(s) + stopPenalty

How the Best Stop Is Chosen

For a one-stop plan, the requests are sorted and the scheduler selects a weighted percentile floor. The percentile is derived from the relative pain of climbing versus descending stairs:

q = upWeight / (upWeight + downWeight)

With the default values:

q = 3 / (3 + 1) = 0.75

So the algorithm selects approximately the 75th percentile floor from the sorted request list. This intentionally biases the stop upward so that fewer passengers are forced to walk up, which is the more expensive action in the model.

In code, for n sorted requests, the stop index is:

index = ceil(q * n) - 1

Two-Stop Optimization

If two stops are allowed, the sorted request list is split at every possible cut position. The left and right groups are optimized independently, and the total cost is calculated as:

C_2 = C_walk(leftGroup, leftStop) + C_walk(rightGroup, rightStop) + 2 * stopPenalty

The scheduler compares the best one-stop plan with all possible two-stop plans and chooses:

Final plan = min(C_1, C_2)

This ensures that an extra stop is added only when it reduces enough walking cost to justify the delay introduced by the stop itself.

System Architecture

  • Frontend built in React 18 with Vite for fast development and build performance.
  • Pure client-side execution, so the prototype has no backend dependency.
  • Interactive queue management with floor tapping, undo, clear queue, and live recalculation.
  • Responsive kiosk-style UI designed for desktop and tablet presentation.
  • Detailed explanation panel to support demonstration, validation, and academic presentation.

Technical Value

From an engineering perspective, the project is useful because it turns a real building-management problem into a measurable optimization problem. The scheduler is explainable, quick to compute, and easy to tune using sliders for upward walking cost, downward walking cost, and maximum stops. Because the current design is rule-based and transparent, it is also a strong foundation for future extensions such as time-based traffic modelling, adaptive penalties, or integration with real elevator hardware and sensors.

In conclusion, LiftPilot is a practical and technically sound prototype for smart building mobility. Its main contribution is not just a working interface, but a clear scheduling logic that balances passenger comfort with lift efficiency using a weighted mathematical model.
